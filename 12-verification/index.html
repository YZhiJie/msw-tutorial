12. 验证体系：让「本地全绿」真的可信 ​

到第十一章为止，我们已经把 Mock 的行为用矩阵定义清楚了。但矩阵本身不会自动站岗：

  • 清单里新增了一个端点，handler 忘了写，类型检查照样通过；
  • 文档表格改成了新路径，Mock 还停在旧路径，构建也不会报错；
  • 某个 handler 的成功状态码从 201 改成 200，单元测试只测了「能返回 JSON」；
  • 覆盖率 90%，但最关键的 412 / 429 分支一次都没跑过。

本章解决的问题是：把「文档写了什么、清单声明什么、Mock 实际做了什么」变成一条能自动失败的验证链。

12.1 四层验证，各管一件事 ​

层回答的问题命令失败时通常意味着
L1 静态契约清单、handler 注册、文档表格、snippet 是否四方一致？版本元数据是否合法？pnpm contract:check有人只改了一边：加了接口没写 handler / 改了路径没改文档
L2 契约单测Schema、客户端、版本协商这些共享代码是否按约定工作？pnpm test:contract契约包自身逻辑回归
L3 行为测试每个 handler 的状态码、错误体、矩阵 F1–F11 是否成立？pnpm test:mocks业务分支写错或行为矩阵被破坏
L4 契约存活测试清单里的每个端点在运行时是否真的能被 Mock 接管？pnpm test（含 contract-survival）handler 没注册、路径写错、鉴权/校验把正常请求也拦了
L5 构建React / Vue / VitePress 三端是否还能编译？pnpm build类型或打包配置问题，常出现在「只跑测试不跑构建」时

覆盖率是 L3 的附加门禁，不是单独一层：它保证「测过的代码比例」，不保证「测对了行为」。两者缺一不可。

12.2 契约存活测试：用清单驱动真实请求 ​

普通单元测试是「我想测什么就写什么」，容易漏掉新端点。契约存活测试反过来：遍历 API_ENDPOINTS，每个端点都必须发一次真实请求。

核心结构（完整实现见 packages/mocks/test/contract-survival.test.ts）：

ts
import { API_ENDPOINTS, CONTRACT_HEADERS } from "@msw-tutorial/contract";

for (const endpoint of API_ENDPOINTS) {
  const fixture = fixtureFor(endpoint, ctx); // 每个端点一份最小合法请求
  const res = await send(fixture);

  // 1. 确实被 Mock 接管（X-Mock 由契约中间件回写）
  expect(res.headers.get(CONTRACT_HEADERS.mock)).toBe("true");
  // 2. 状态码与清单声明一致
  expect(res.status).toBe(endpoint.successStatus);
}

三个设计要点：

  1. 夹具集中在一处：fixtureFor() 用 switch (endpoint.id) 为每个端点准备最小合法请求（登录令牌、存在的 ID、合法 body）。
  2. 漏配会立即失败：default 分支直接抛错「清单新增了端点 X，请补一个存活夹具」。新增接口时，测试会强制你回来补请求参数，而不是悄悄跳过。
  3. 断言只依赖契约元数据：不写死 200、不写死路径字符串，端点改路径后测试自动跟着走；只有「清单声明与运行时行为不一致」才会红。

失败时怎么读：

现象最可能的原因
X-Mock 为 nullhandler 没注册，请求被放行到真实网络
404handler 路径与清单不一致（注意通配前缀 */api/...）
401 / 422夹具缺少令牌或必填字段，或鉴权/校验条件被改严
状态码不符handler 的 status 与清单 successStatus 漂移

GraphQL 不走 REST 的契约头装饰，因此单独断言「清单能发现端点 + 返回 { data } 信封」，见同文件第二个用例。

12.3 场景化测试：把一次偶发 bug 变成永久用例 ​

scenarioStore 不只是给人玩的开关，它让「异常路径」可以被稳定复现：

ts
// 强制全局错误：所有业务 handler 都应短路返回 503
scenarioStore.patch({ errorMode: "force", forceStatus: 503 });
const res = await jsonFetch("/users");
expect(res.status).toBe(503);

// 延迟归零：避免每个用例都真的等 100ms
scenarioStore.patch({ latencyMs: 0 });

// 关闭鉴权：验证「本地无令牌也能开发」
scenarioStore.patch({ authEnabled: false });

推荐工作流：

步骤做法
1. 复现用场景开关或特定请求手动复现 bug
2. 固化把最小请求写进对应 *.test.ts，先确认它会红
3. 修复改 handler / 契约，直到用例转绿
4. 回归用例永久留在套件里，后续重构不会悄悄复发

注意：scenarioStore 是全局单例。测试夹具在 beforeEach 里统一 reset，否则前一个用例开的「强制 500」会污染后一个用例。

12.5 CI 分层与本地一键验证 ​

CI（.github/workflows/ci.yml）按「越快越靠前」排序，失败时能第一时间定位：

顺序步骤典型失败原因
1pnpm typecheck跨包类型漂移、可选属性与 exactOptionalPropertyTypes
2pnpm lint边界违规（如示例应用直接 import mocks）、未使用变量
3pnpm test行为回归、契约存活失败
4pnpm test:coverage新增分支没测到，拉低全局覆盖率
5pnpm contract:check清单 / handler / 文档 / snippet 四方漂移
6pnpm build三端编译或 VitePress 构建失败
7pnpm comics:check漫画资源规范

本地不想逐个敲？用一条命令跑完全部六道门禁：

bash
pnpm verify          # 等价于按顺序执行 typecheck → lint → test → coverage → contract:check → build
pnpm verify --list   # 只看步骤，不执行
1
2

verify 遇到第一个失败就停下，并打印「哪一步、耗时、怎么单独重跑」，避免出现「最后一步绿了，其实前面早挂了」的假象。

12.6 可复现性：不稳定测试的五个来源 ​

来源症状本项目的处理
随机数据每次 ID / 数量不同Faker 固定种子 20261001，resetDb() 还原
跨用例状态单独跑绿、全量跑红beforeEach 重置 db / 幂等缓存 / 限流 / 场景
真实时间延迟、限流窗口漂移测试里 latencyMs: 0；限流用例用独立 key
真实网络CI 上偶发超时所有请求走 setupServer 拦截，不访问外网
固定 sleep慢机器上偶发失败异步 WebSocket 用 waitFor(predicate) 轮询

packages/mocks/test/setup.ts 是这些约定的落脚点：

ts
beforeAll(() => server.listen({ onUnhandledFrame: "error" }));
beforeEach(() => {
  resetDb();
  resetContractState();
  resetRateLimit();
  scenarioStore.reset();
  scenarioStore.patch({ latencyMs: 0 });
});
afterEach(() => server.resetHandlers());
afterAll(() => server.close());

维护规则：矩阵新增一行，就要能在上表找到对应测试；找不到就先补测试，再宣称行为已落地。

12.8 常见坑 ​

坑后果建议
只测 happy path401 / 412 / 429 分支永远没跑过每个写接口至少补一个失败用例
断言实现细节重构后测试全红，但行为没变断言「响应状态 + 对外字段 + 头」，不查内部函数
在测试里 sleep慢机器上偶发失败用 waitFor 轮询，或让 handler 零延迟
共享可变状态用例顺序一变就红beforeEach 全量 reset，用例内不依赖执行顺序
覆盖率刷分测试数量涨、缺陷没少以行为矩阵为准，阈值只做地板

12.9 练习 ​

  1. 在 API_ENDPOINTS 里新增一个 GET /api/ping，只改清单不写 handler，依次跑 pnpm contract:check 和 pnpm test，观察两条链路分别如何报错。
  2. 把 createUser 的 successStatus 从 201 改成 200（不改 handler），看存活测试的失败信息能否直接指出端点。
  3. 给 412 分支补一个「If-Match 恰好命中」的正向用例，确保乐观并发不会误伤正常请求。
  4. 用 pnpm test:coverage 打开 HTML 报告，找出一个未覆盖分支，判断它是「环境不可达」还是「真的缺测试」。
