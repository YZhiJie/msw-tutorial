10. 请求层韧性：超时、重试、并发合并与单飞刷新 ​

第九章让「数据契约」可执行；本章让「请求过程」可预期。

企业项目里最常见的线上事故不是接口写错，而是：

  • 某个请求卡住 30 秒，页面一直转圈；
  • 弱网下 502 直接失败，没有重试；
  • 用户连点两次「创建」，产生两条脏数据；
  • 列表页三个组件同时请求 /users，后端被打三次；
  • 令牌过期瞬间 10 个请求同时触发刷新，刷新接口被打爆。

这些都不该由业务页面各自解决。本章把它们收口到共享客户端 packages/contract/src/client.ts。

10.1 一次逻辑请求的生命周期 ​

  │ 相同 method+url+token 的飞行中请求 → 共享同一个 Promise

10.4 并发合并（dedupe） ​

同一时刻多个组件请求同一个 GET，客户端只发一次：

ts
const [a, b] = await Promise.all([
  client.request("/users?page=1"),
  client.request("/users?page=1"),
])
// 实际只发 1 次 HTTP，两个调用方各拿到独立响应副本
1
2
3
4
5

实现要点：

  • key = method + url + Authorization，避免把不同用户的响应混在一起；
  • 只对无 body 的 GET 生效；
  • 共享的是「飞行中的 Promise」，每个调用方仍然各自解析、各自记日志；
  • 请求结束立即从 map 删除，不会把失败结果缓存给后续请求。

需要缓存语义时不要用 dedupe，应该引入独立的缓存层（过期时间、失效策略是另一套问题）。

10.5 401 单飞刷新 ​

ts
const client = createApiClient({
  baseUrl: "/api",
  getAccessToken: () => session.accessToken,
  onUnauthorized: async () => {
    const res = await fetch("/api/auth/refresh", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ refreshToken: session.refreshToken }),
    })
    if (!res.ok) return null
    const data = (await res.json()) as { accessToken: string }
    session.setAccessToken(data.accessToken)
    return data.accessToken
  },
})

注意：

  • onUnauthorized 只会在请求确实带了令牌时触发，登录失败不会误触发刷新；
  • 每个逻辑请求最多刷新重放一次，避免「刷新失败 → 再 401 → 再刷新」的死循环；
  • 刷新失败后要清理会话，让用户重新登录——这是业务层职责，客户端只负责返回 null。

10.7 本章你要动手的事 ​

  1. 在示例应用里给列表请求加 timeoutMs: 3000，观察 Mock 延迟场景下的 TIMEOUT；
  2. 用 AbortController 实现「切换页面时取消未完成请求」；
  3. 把创建用户的调用改成 idempotencyKey: true，连点两次，确认只创建一条；
  4. 给两个并发 GET /users 打开日志，确认 attempts=1 且实际只发一次。
