9. 可执行契约：从「文档约定」到「运行时门禁」 ​

第八章解决了「类型和路径只有一份」，但还留了两个企业级缺口：

  1. 字段规则仍靠手写 if：name 至少 2 位、email 要合法、role 只能是枚举——这些规则写在 handler 里，文档里再抄一遍，测试里再猜一遍。
  2. 版本只认一个值：SUPPORTED_API_VERSIONS 只有当前版本，没有「旧版本还能用多久」「什么时候必须下线」的演进信息。

本章把契约再往前推一步：规则可执行、版本可演进。所有代码都在仓库里可以直接运行。

9.1 把字段规则写成 Schema ​

新增文件 packages/contract/src/schema.ts 提供一套零依赖的校验器：

ts
import { createUserSchema } from "@msw-tutorial/contract";

const result = createUserSchema.validate({
  name: "x",
  email: "not-an-email",
  role: "root",
  password: "123",
});

if (!result.ok) {
  console.log(result.issues);
  // [
  //   { path: "name",     message: "name至少 2 个字符" },
  //   { path: "email",    message: "email 格式不正确" },
  //   { path: "role",     message: "只能是 admin 或 member" },
  //   { path: "password", message: "password至少 6 个字符" }

为什么不用 zod？ ​

zod 当然好用，但教程的目标是让读者看懂校验器内部发生了什么。本项目的实现只有约 150 行，包含：

构造器作用典型参数
string()字符串 + 长度/正则min、max、pattern、message
enumOf()字符串枚举["admin", "member"]
boolean()布尔值—
array()数组 + 元素 schema + 长度min、max
optional()缺省跳过，显式 null 仍报错—
object()按 shape 校验，丢弃未知字段—

object() 返回的是只包含已声明字段的新对象，因此前端可以放心把 body 直接交给业务逻辑，不用担心 __proto__、isAdmin 之类的多余字段被透传。

与类型对齐 ​

Schema 用映射类型约束每个字段，字段名写错或漏写会在编译期报错：

ts
export const createUserSchema: Schema<CreateUserInput> = object<CreateUserInput>({
  name: string({ min: 2, label: "name" }),
  email: string({ pattern: EMAIL_RE, message: "email 格式不正确", label: "email" }),
  role: optional(enumOf(["admin", "member"] as const)),
  password: optional(string({ min: 6, label: "password" })),
});

9.2 让版本可以演进 ​

真实企业的 API 不会永远只有一个版本。新增字段还算兼容，删除字段、改语义、改错误码就必须给调用方迁移窗口。

新增文件 packages/contract/src/versions.ts 把版本从「一个常量」升级为「一张可校验的元数据表」：

ts
export const API_VERSION_META = {
  "2026-10-01": {
    status: "current",
    releasedAt: "2026-10-01",
    notes: "当前版本：统一错误信封、标准请求头与幂等语义",
  },
  "2026-06-01": {
    status: "legacy",
    releasedAt: "2026-06-01",
    sunsetAt: "2027-06-01",
    notes: "旧版本：缺少 X-Response-Time 与幂等冲突 409 语义，计划日落",
  },
} as const satisfies Record<string, ApiVersionMeta>;

export const API_VERSION = "2026-10-01";
export const SUPPORTED_API_VERSIONS = Object.keys(API_VERSION_META);

版本演进检查清单 ​

改动是否破坏兼容处理方式
新增可选响应字段否直接发版，更新 notes
新增必填请求字段是新版本 + 旧版本默认值
删除响应字段是先标 legacy，给一个 sunset 窗口
修改错误码/错误信封是新版本，旧版本保留映射层
仅修改文档措辞否不改版本号

contract:check 自动兜底 ​

pnpm contract:check 现在同时校验版本元数据：

  • API_VERSION 必须指向 status: current；
  • SUPPORTED_API_VERSIONS 与 API_VERSION_META 必须双向一致；
  • 每个 legacy 版本必须有 sunsetAt，且不能已经过期。

任何一条不满足，CI 直接失败。这样「忘记写日落日期」不会拖到线上才发现。

9.3 本章你要动手的事 ​

  1. 给 packages/contract/src/schema.ts 增加 listUsersQuerySchema，把 role / sort 的枚举校验也收进契约；
  2. 在 packages/mocks/src/handlers/users.ts 的列表 handler 里消费它，非法 role 从 400 改成 422（记得同步测试）；
  3. 新增一个 2027-01-01 版本，写清 notes、把旧版本状态改成 legacy 并设置 sunsetAt；
  4. 跑 pnpm typecheck && pnpm test && pnpm contract:check，确认三处都过。

9.4 常见坑 ​

坑现象规避
Schema 与类型双写改类型后校验仍用旧规则用 Schema<T> 映射类型，让 typecheck 兜底
校验器做业务查询校验层查数据库，产生竞态Schema 只校验结构，唯一性留给 handler
旧版本直接删老客户端 400 雪崩先 legacy + Deprecation/Sunset，再下线
只校验 Mock 不校验前端前端提交脏数据，Mock 才发现前端表单提交前复用同一 schema（可选）

下一章会把注意力从「数据长什么样」转到「请求失败怎么办」：超时、重试、并发去重与刷新令牌，这些才是企业项目里真正难写的部分。
