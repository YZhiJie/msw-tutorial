8.1 同一套 API 文档驱动前后端 ​

前后端并行开发最怕三件事：

  1. 文档漂移：接口文档写的是 rows，前端拿到的是 data；文档说 PUT，实现是 PATCH。
  2. Mock 失真：Mock 永远返回 200 和固定数据，联调时才发现 401 / 409 / 422 / 幂等重放全没覆盖。
  3. 切换成本高：Mock 代码散落在页面里，接真实后端时要逐个文件删改。

本项目的解法是引入 @msw-tutorial/contract：把「文档」变成可执行的单一契约源，让前端、Mock、文档站、测试都从同一个包取定义。

契约包的四层结构 ​

text
packages/contract/
├── src/
│   ├── types/          # 领域类型：按业务拆分 auth / user / post / file / scenario
│   ├── endpoints.ts    # 接口清单：方法、路径、鉴权、幂等、成功状态码
│   ├── headers.ts      # 契约请求头：X-Request-Id / X-Api-Version / Idempotency-Key…
│   ├── runtime.ts      # 运行时配置：mock | real、baseUrl、版本、语言
│   └── client.ts       # 共享 HTTP 客户端：统一注入请求头、错误与日志

前端与后端如何并行 ​

推荐按下面的顺序推进，双方在同一周内就能各自开工：

  1. 先定契约：产品/后端/前端一起把路径、请求体、响应体、错误码、请求头写进 packages/contract。
  2. 后端实现真实接口：严格按 types 与 endpoints 落库；新增字段先改契约再改代码。
  3. 前端基于 Mock 开发：页面只依赖共享客户端，不关心数据来自 MSW 还是真实网关。
  4. 契约测试兜底：Mock 层用测试覆盖成功、鉴权失败、参数校验、幂等重放等分支。
  5. 后端就绪后切环境：只改 .env.real，业务代码零改动。

关键约束：页面禁止直接 fetch("/api/...")，必须走 createApiClient。这样请求头、错误信封、日志口径才能保持一致。

统一响应约定 ​

所有 JSON 接口遵循同一套外壳：

ts
// 成功：直接返回业务数据或分页壳
interface Paginated<T> {
  data: T[]
  page: number
  pageSize: number
  total: number
  totalPages: number
}

// 失败：统一错误信封
interface ApiErrorBody {
  error: {
    code: string        // BAD_REQUEST / UNAUTHENTICATED / CONFLICT / VALIDATION_ERROR…
    message: string
    details?: unknown
  }
}

共享客户端的最小用法 ​

ts
import { createApiClient } from "@msw-tutorial/contract"

const client = createApiClient({
  baseUrl: "/api",
  apiVersion: "2026-10-01",
  clientVersion: "react-example-1.0.0",
  locale: "zh-CN",
  getAccessToken: () => session.token,
  onLog: (entry) => requestLog.push(entry),
})

// 自动带 X-Request-Id / X-Api-Version / X-Client-Version / Accept-Language
await client.request<User[]>("/users", { query: { page: 1, pageSize: 20 } })

// 写操作自动生成幂等键：重试不会重复创建
await client.request<User>("/users", {
  method: "POST",
  body: { name: "张三", email: "zhangsan@example.com" },
  idempotencyKey: true,
})

验收清单 ​

  • [ ] 新增接口时，先改 contract 再改页面/Mock。
  • [ ] 页面没有裸 fetch，也没有硬编码 /api。
  • [ ] 错误分支使用统一错误信封，而不是各写各的 { success: false }。
  • [ ] 写操作考虑幂等键；列表接口覆盖分页与筛选参数。
  • [ ] 文档表格与实际 handler 一一对应。
