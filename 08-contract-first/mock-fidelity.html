8.2 让 Mock 与真实接口一致 ​

「Mock 能用」和「Mock 可信」是两件事。可信的 Mock 至少要在这些维度与真实接口对齐：

维度真实后端通常怎么做本项目 Mock 的做法
自定义请求头网关注入/校验 X-Request-Id、X-Api-VersionwithContract() 统一校验与回写
参数负载校验类型、必填、枚举、长度handler 内逐字段校验，返回 422 + details
鉴权Bearer 令牌、过期、权限requireAuth() + 角色/自删校验
状态码201 / 204 / 401 / 403 / 409 / 422按契约返回，不用 200 包一切
幂等Idempotency-Key 重放首次结果withIdempotency() 内存缓存 + 负载指纹
分页/筛选页码、页大小、关键词、排序intParam() / strParam() 解析并夹取范围，非法枚举返回 400
下载Content-Disposition + 二进制文本/CSV/PNG 三种真实响应
网络失败网关超时、连接中断HttpResponse.error() 让 fetch 直接 reject

自定义请求头 ​

契约头定义在 packages/contract/src/headers.ts，客户端自动注入，服务端统一回写：

请求头方向作用
X-Request-Id客户端 → 服务端 → 响应链路追踪；Mock 缺省会自动生成并回写
X-Api-Version客户端 → 服务端版本协商；不在白名单返回 400
X-Client-Version客户端 → 服务端 → 响应灰度、排障、最低版本拦截
Accept-Language客户端 → 服务端 → Content-Language本地化错误文案
Idempotency-Key客户端 → 服务端写操作重试去重
X-Mock服务端 → 客户端一眼识别当前响应来自 Mock
X-Response-Time服务端 → 客户端服务端处理耗时

请求检查器会同时展示请求头和响应头，可以直接看到这些头在两端是否一致：

用外观统一响应行为 ​

MSW handler 原本每写一个接口都要手动加响应头。本项目把 http 换成了同构的 contractHttp：

ts
// before
import { http } from "msw"
http.get("*/api/health", () => HttpResponse.json({ status: "ok" }))

// after：所有响应自动获得契约头、版本协商与耗时统计
import { contractHttp as http } from "../contract.js"
http.get("*/api/health", () => HttpResponse.json({ status: "ok" }))

withContract() 做的事情：

  1. 校验 X-Api-Version，不在白名单直接 400；
  2. 回写 X-Request-Id（请求没带就生成）；
  3. 回写 X-Api-Version、X-Client-Version、Content-Language；
  4. 添加 X-Mock: true、X-Response-Time、Cache-Control: no-store 与 Vary；
  5. Response.error() 与 passthrough() 不装饰，保留原始网络语义。

参数负载校验 ​

Mock 不是「随便回点数据」，而是先按真实后端的规则校验：

ts
const input = validateUserBody(body)
if (typeof input === "string") {
  return fail(422, "参数校验失败", { field: input })
}
if (db.users.some((u) => u.email === input.email)) {
  return fail(409, `邮箱 ${input.email} 已存在`)
}

覆盖的典型规则：

  • 必填字段缺失 → 422
  • 类型错误（例如 pageSize: "abc"）→ 列表解析回落默认值或 422
  • 枚举非法（role: "owner"）→ 422
  • 唯一键冲突（邮箱重复）→ 409
  • 未登录 / 令牌过期 → 401
  • 权限不足（非 admin、自删）→ 403

幂等：写操作重试不重复创建 ​

真实支付/订单类 API 常用 Idempotency-Key。Mock 用负载指纹实现同样的语义：

ts
return withIdempotency(request, JSON.stringify(input), () => {
  const { user } = db.createUser(input)
  return HttpResponse.json({ user }, { status: 201 })
})

  • 相同 Key + 相同负载：直接返回首次响应（相同 user id）。
  • 相同 Key + 不同负载：返回 409，提示该 Key 已用于其他请求。
  • 未带 Key：退化为普通请求。

分页、筛选与排序 ​

列表 handler 用 packages/mocks/src/lib/query.ts 的小工具逐个解析参数，再交给假数据库。 真实项目里字段更多时，可以在此基础上抽成统一的 parseListQuery()：

ts
const url = new URL(request.url)
const role = strParam(url, "role")
if (role !== undefined && role !== "admin" && role !== "member") {
  return fail(400, "role 查询参数只能是 admin 或 member")
}

const result = db.listUsers({
  page: intParam(url, "page", 1),
  pageSize: Math.min(intParam(url, "pageSize", 20), 100),
  q: strParam(url, "q"),
  role: role === "admin" || role === "member" ? role : undefined,
  sort: (strParam(url, "sort") as "createdAt" | "-createdAt" | "name" | "-name" | undefined)
    ?? "-createdAt",
})

网络层失败 ​

fetch 失败与 HTTP 错误是两种语义。Mock 用 HttpResponse.error() 让客户端进入 catch：

  • 网络失败：客户端记录 status: 0，抛出 ApiError(0, NETWORK_ERROR)。
  • HTTP 4xx/5xx：正常拿到响应，客户端解析错误信封后抛 ApiError(status, body)。

契约测试 ​

Mock 的「真实感」需要测试兜底。推荐至少覆盖：

  • 成功路径（200/201/204）
  • 鉴权失败（401）
  • 权限不足（403）
  • 参数校验（422）
  • 唯一冲突（409）
  • 幂等重放与负载冲突
  • 版本协商（400）
  • 响应头回写
